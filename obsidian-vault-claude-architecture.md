# Obsidian Vault Classifier & Recommender — Architecture Guide

A working reference for building a program that calls the Claude API to classify
notes and recommend actions based on the contents of an Obsidian vault.

---

## 1. Core Principle: You Are the Memory Layer

The Claude API is stateless. Nothing about "the vault" persists between calls
unless you put it there yourself. This reframes the whole project as a
**retrieval and context-construction problem**, not a "give Claude the vault"
problem. Every design decision below follows from this.

---

## 2. High-Level Architecture

```
Obsidian Vault (plaintext .md files)
        │
        ▼
 [1] Vault Indexer  ──────────────► Index Store
   (parse, chunk,                  (SQLite / JSON / vector DB)
    extract metadata)
        │
        ▼
 [2] Retriever
   (decide what's relevant
    to the current task)
        │
        ▼
 [3] Prompt Constructor
   (assemble focused context)
        │
        ▼
 [4] Claude API Call
   (classify / recommend)
        │
        ▼
 [5] Action Layer
   (write back to vault, log,
    surface to user)
```

Each stage is independent and swappable — start simple, upgrade pieces as
the vault grows.

## 3. Stage 1: Indexing the Vault

### What to extract per note
- **Frontmatter** (YAML): tags, dates, aliases, custom fields — cheap, structured signal
- **Title / filename**
- **Body text**
- **Wikilinks** (`[[Note Name]]`) and backlinks — the graph structure is a first-class signal, don't throw it away
- **Headings** — useful for chunking (see below)
- **Last modified time** — useful for recency-based recommendations

### Chunking strategy
Obsidian notes vary wildly in length. Rules of thumb:

| Note size | Strategy |
|---|---|
| Short (<500 tokens) | Treat as one chunk |
| Medium | Chunk by top-level heading (`##`) |
| Long / structured (MOCs, daily logs) | Chunk by heading + fall back to fixed-size (~500–800 token) windows with overlap |

Keep a stable `chunk_id` (e.g., `filepath#heading-slug`) so you can always map
a chunk back to its source file and re-fetch full context later.

### Where to store the index
- **Small vault (<1–2k notes):** SQLite with a table of chunks + metadata. No embeddings needed yet — full-text search (SQLite FTS5) gets you far.
- **Larger vault / semantic search needed:** add a vector store (e.g., a local one like `sqlite-vec` or `chroma`, or hosted like Pinecone/Qdrant) storing embeddings per chunk. Keep the SQLite metadata table either way — embeddings are only for *finding* relevant chunks, not for storing the actual content Claude needs to see.

## 4. Stage 2: Retrieval — Deciding What Claude Sees

This is the highest-leverage part of the whole system. Options, roughly in
order of complexity:

1. **Direct file read (no retrieval)** — for a specific, targeted task ("classify this one note"), just read that file straight off disk and send it. No index needed.
2. **Metadata filter** — e.g., "all notes tagged `#project` modified in the last 7 days." Fast, deterministic, no embeddings required.
3. **Full-text search** — keyword match via SQLite FTS5 or ripgrep over the vault. Good middle ground, cheap to build.
4. **Embedding similarity search** — needed when the task is semantic ("find notes related to this idea" rather than "find notes containing this word"). Use Claude's embeddings or any embedding model; store vectors in your index.
5. **Graph-based retrieval** — walk wikilinks/backlinks N hops from a seed note. Obsidian vaults are graphs; for "related notes" recommendations this often outperforms pure semantic search.

**In practice:** combine 2–3 of these. E.g., filter by tag/date first (cheap), then rank the remaining candidates by embedding similarity (only where needed), then include directly linked notes regardless of rank (graph signal overrides pure similarity).

## 5. Stage 3: Prompt Construction

- **One task, one focused prompt.** Don't build one mega-prompt that tries to classify *and* recommend *and* summarize the whole vault at once. Separate calls per task are easier to evaluate and cheaper to run selectively.
- **Structure the context explicitly** — wrap each retrieved note/chunk in tags so Claude can distinguish "vault content" from your instructions:

```
<note path="Projects/Q3 Launch.md" modified="2026-08-01">
...chunk content...
</note>
```

- **Use structured output** for classification tasks — ask for JSON matching a fixed schema (e.g., `{"category": "...", "confidence": ..., "reasoning": "..."}`) so results are directly usable downstream, not something you have to re-parse from prose.
- **Keep prompts small.** Context rot is real — a 1M-token window doesn't mean you should fill it. For a classification task, the 5–10 most relevant chunks usually beat dumping 200.

---

## 6. Stage 4: Calling the API

- **Batch where possible.** If you're classifying hundreds of notes on a schedule (e.g., nightly), use the [Batch API](https://platform.claude.com/docs/en/build-with-claude/batch-processing) — significantly cheaper than sequential real-time calls, and this workload is not latency-sensitive.
- **Cache the stable parts.** If your system prompt / instructions are constant across many notes, use [prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching) so you're not re-paying for the same instructions on every call.
- **Pick the right model for the task.** Classification of individual notes against a fixed taxonomy is a good fit for a smaller/faster model (e.g., Haiku); open-ended "what should I do with this vault" recommendations benefit from a stronger model (e.g., Sonnet/Opus). Don't default to the biggest model for every call.
- **Use the token counting API** before sending, if you're batching many notes with variable length, to avoid surprises.

---

## 7. Stage 5: Acting on Results

- **Write-back to the vault:** if recommendations should appear as frontmatter tags, a "Suggested Actions" section, or a linked note, write plain Markdown/YAML back to the `.md` file — Obsidian will pick up changes on next open. Be careful with concurrent edits if Obsidian is open at the same time (file watchers, conflict markers).
- **Keep a separate log/index of past classifications** rather than only mutating notes in place — lets you track drift, debug bad classifications, and avoid re-processing unchanged notes (hash the content, skip if unchanged since last run).
- **Human-in-the-loop for the first pass:** surface recommendations for approval before auto-writing, until you trust the classifier's precision on your specific vault's conventions.

---

## 8. Suggested Build Order (MVP → Full System)

1. **Script that reads N specified notes and classifies them** — no index, no retrieval, just direct file → Claude call → printed result. Validates prompt design first.
2. **Add the SQLite index** — frontmatter, tags, links, chunked bodies. Add a CLI to re-index on demand.
3. **Add full-text/metadata retrieval** — wire a real "find relevant notes for X" step.
4. **Add write-back** — start with a dry-run mode that prints proposed changes before writing.
5. **Add scheduling/batching** — nightly batch job over the whole vault using the Batch API.
6. **Add embeddings/graph retrieval** — only once keyword/metadata retrieval proves insufficient for the recommendation quality you want.

Resist building 4–6 before 1–3 are working well on a real subset of your vault — retrieval quality is much easier to evaluate once you can see actual classification output.

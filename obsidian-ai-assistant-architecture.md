# Obsidian AI Assistant — Architecture Guide

A knowledge-retrieval and pattern-discovery architecture for an AI assistant that introspects an Obsidian vault, finds patterns in its contents, and suggests new research directions.

Broken into four layers: indexing pipeline, storage, retrieval, and pattern discovery — plus a suggested build order.

---

## 1. Indexing Pipeline

Runs incrementally, on file change — not as a full re-index every time.

**Trigger:** the Obsidian plugin watches vault file events (create/modify/delete), debounces them, and queues changed files rather than reprocessing the whole vault.

**Steps per changed note:**

1. **Parse** — strip frontmatter, extract existing `[[wikilinks]]`, `#tags`, and headers separately from body text. These are free, high-confidence graph edges the user already built by hand — don't discard them.
2. **Chunk** — split by heading/paragraph rather than fixed token windows where possible; Obsidian notes are usually already semantically segmented by the user's own headers. Keep a pointer back to source file + line range for every chunk.
3. **Embed** — run each chunk through a local embedding model (e.g., a small BGE/E5 variant via ONNX or `candle` in Rust, or a Python sidecar if you want access to a wider model zoo). Store the resulting vectors.
4. **Extract triples** — send chunk text to an LLM (local via Ollama, or an API) with an open-schema extraction prompt: *"list (subject, relation, object) triples, using noun phrases as they appear in the text."* No predefined ontology — let structure emerge. This is the expensive step, so batch it and only re-run it for changed chunks.
5. **Merge into graph** — new triples become nodes/edges. Use embedding similarity between noun phrases to add "synonym" edges (e.g., cosine similarity > 0.8) so that, say, "ffi bindings" and "foreign function interface" resolve to the same conceptual node without hand-building an alias table. This mirrors HippoRAG's approach and is worth replicating directly.

## 2. Storage

- **Graph store:** something embeddable rather than a server. SQLite with a triples table (`subject, relation, object, source_note, source_chunk`) works fine at vault scale (thousands, not millions, of notes) and keeps the plugin self-contained. Kuzu is worth a look if you want real graph-query ergonomics (Cypher-like) without running a separate DB process.
- **Vector store:** the same SQLite file with `sqlite-vec`, or a small local vector index (hnswlib, or Rust's `instant-distance`) if you want faster approximate nearest-neighbor search. No need for a hosted vector DB at personal-vault scale.
- Keep both stores keyed by the same chunk/note IDs so you can always jump from a graph node back to the source vector and the raw text.

## 3. Retrieval Layer

On a query (a user question, or a periodic "what's interesting in here" scan):

1. Extract entities/keywords from the query the same way entities are extracted from notes.
2. Seed **Personalized PageRank** on the graph from those entity nodes — the associative "spread activation" step. This is cheap to run (sparse matrix-vector multiplication), trivially fast in Rust with something like `petgraph` or a hand-rolled CSR matrix.
3. Rank passages by aggregating PPR mass across their member nodes, weighted by the inverse document frequency of each node (rare nodes count more — this is HippoRAG's "graph-native IDF," and it does a lot of the work).
4. Optionally re-rank the top candidates with straight vector similarity as a second pass, so results combine associative reach with semantic precision.

## 4. Pattern-Discovery / Suggestion Layer

This is the part that's genuinely novel relative to existing Obsidian AI plugins, and it's mostly graph algorithms available for free once the retrieval layer exists:

- **Community detection** (Louvain or label propagation over the graph) to surface clusters — e.g., "these 40 notes form a tight cluster around X" — as candidate topics worth a MOC (map of content) note.
- **Bridge / boundary nodes** — nodes with high betweenness centrality sitting between two otherwise-disconnected clusters are the best "unexplored research direction" candidates: they're where two things studied separately turn out to touch.
- **Low-connectivity recent notes** — notes added recently with few graph edges are either genuinely novel territory (worth surfacing: "you haven't connected this to anything yet") or under-processed (worth re-running extraction on).
- **Orphaned high-PPR nodes** — concepts that show up frequently across extracted triples but never got their own note. These are implicit topics touched repeatedly without being formalized — a natural "suggest research on X" signal.

## Suggested Build Order

1. Ship the flat vector-search baseline first — useful as a fallback and a sanity check for everything built on top of it.
2. Add the wikilink/tag graph as free structure — no LLM needed yet.
3. Layer in LLM triple extraction, merged into the same graph.
4. Add PPR-based retrieval.
5. Add the community-detection / bridge-node suggestion pass as a periodic background job (e.g., nightly), surfaced as a sidebar panel rather than computed live.
